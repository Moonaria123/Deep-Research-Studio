# Windows 客户端验收

客户端分支为 `codex/gen1-windows-client`，基于已发布第一代 Web 提交
`cace08540495604605623aae843b9a21525df6bd`。升级的起点采用
[上一轮实际交付的 Alpha.1](windows-client-validation-20261118.md)，安装包 SHA-256 为
`328290dc74c53480762389e39b8a5c7f26da65fa755abbad387ad95b538fda4e`。

本轮在原生 WebView2 中操作客户端，在独立 Windows Sandbox 中执行安装程序。
真实研究使用单独的桌面数据目录，经客户端配置接口把凭据写入 Windows DPAPI 凭据库。

验收安装包为 `Deep Research Studio_1.1.0-alpha.3_x64-setup.exe`，33,096,242 字节，
SHA-256 为 `57db92560c21d96a87d7c2f7cabb183248d37f0a7faac0d98d7bd4c94cb9abff`。
安装后的壳程序和 API 的 SHA-256 分别为
`bacb081fbce039be36ccee923c7e087e88bef34df9003afa95515461b1a28d6e` 和
`8c87c3518ee410e5f868508fbb868b29e59178f0c2a6653d555e577f0a91da0b`。

## 已修正的问题

- 资料库曾把独立导入记录显示为一次关联研究，链接指向空会话。现在只有含运行或
  会话 ID 的记录会出现在关联列表，导入来源仍保存在资料库。
- 壳程序曾在取得独占端口前创建数据目录。现在由 API 在成功绑定端口并校验目标路径后
  创建桌面数据目录。
- 桌面来源链接曾被 Shell 插件拦截，点击时出现权限错误。桌面端为这些链接使用命名窗口目标，
  交给现有的原生 HTTP/HTTPS 打开逻辑，系统浏览器负责显示网页。
- Firecrawl v2 的真实搜索探测返回 HTTP 200，响应中 `success` 为真，`data.web` 为数组。
  设置页原先只接受旧式 `data` 数组，因而拒绝保存有效配置。连接探测和研究运行时现均支持两种结构。

## 验收记录

### 升级前的真实研究

在本机通过 Alpha.1 的 NSIS 安装程序安装客户端，从原生首页选中 Fast Search，提交 SQLite FTS5 的公开问题。
客户端使用 Brave 检索，并通过 Poe 调用 `gpt-5.4`。运行 `run_fe429b40a87d` 以
`completed` 结束。写作调用一次，返回 260 个字符，记录 688 个 token。事件流包含
20 个正文片段和一次完成事件。界面展示一个 SQLite 官方来源，引用覆盖率为 50%。
验收核对了原生页面、写作调用、外部检索和实际引用绑定。关闭原生窗口后 API 端口释放。

可导出。升级后沿用原配置，未重新录入 Brave 或模型凭据。

| --- | --- | --- |

### Alpha.3 安装版的真实研究与导出

从 Alpha.3 History 打开上一版的报告后，界面仍显示原来的 65% 覆盖率。
在原生 Settings 中填写 Firecrawl 并点击 **Save search providers**，保存成功，
搜索与正文提取均为可用。原有 Brave 和 Poe 凭据直接沿用。

在 Deep Research 页重新提交最初未取得引用的 SQLite FTS5、MATCH 与 BM25 问题。
运行 `run_1eb2758363b0` 完成，两次 Brave 搜索获得外部证据，一次 Firecrawl 正文提取成功。
Poe 的 `gpt-5.4` 完成一次写作调用，写作阶段用量为 1,872 token。最终正文 2,313 字符，
产生 98 个正文事件、一个成功完成事件，服务保存了一份完整报告。

界面显示一个 SQLite 官方来源，引用覆盖率为 83%（内部值 0.8333）。
从原生结果页点击 Export，生成 4,114 字节的 Markdown，SHA-256 为
`3947069a2f729366194b7835894f7fe44a787fcca9b9f8c98fa2a800a836821a`。
导出内容标注置信度为 `Uncertain`，并指出所取片段不足以解释 MATCH 查询的完整语法。
窗口正常关闭后，API 与测试调试端口均已释放。

### 干净环境诊断

Windows Sandbox 能安装和卸载 Alpha.1，但第一次启动时，WebView2 Loader 未能找到可用的运行时。
沙箱的 HKLM 版本为 `157.0.4341.42`，磁盘上的 `msedgewebview2.exe` 位于
`157.0.4341.46`。Windows Job API 检查成功。微软在线引导程序和已签名的 x64
Evergreen 独立安装程序都返回 `0x80040902`。

同一沙箱中，仅向旧版进程提供磁盘上的 `157.0.4341.46` 运行时目录，就能打开主窗口并启动 API。
该路径用于给 Alpha.1 写入升级前的测试会话。独立干净沙箱的 Rust 验证中，默认 Loader 返回
`0x80070002`。恢复函数校验了系统目录中浏览器 EXE 与加载 DLL 的路径和微软签名，
自动选中 `157.0.4341.46`，随后 Loader 成功返回该版本。Alpha.2 的整包升级曾出现
一次等待 API 超时，单次超时的原因未能确认。

使用同一份 Alpha.3 NSIS 包，在两个独立的新沙箱中分别完成全新安装和从 Alpha.1 原位升级。
Alpha.3 两次启动都没有预设 WebView2 运行时路径，API 就绪时间分别为 13.007 秒和
12.128 秒。升级保留了原会话，重复启动未创建多余的数据目录；卸载清除了程序、注册表卸载项
和快捷方式，并保留研究数据。详细步骤见[安装验收记录](qa/windows-installer-acceptance-20261118.md)。

宿主机从 Alpha.1 经 Alpha.2 升至 Alpha.3，最终卸载后复核了真实研究的正文哈希、报告行和
测试专用 DPAPI 凭据库；独立测试目录中配置和凭据库均未检出这三项测试密钥的明文。
确认卸载保留数据之后，使用客户端设置逻辑解除了 Poe、Brave 和 Firecrawl 的三项测试凭据引用，
并移除了这次验收专用的无引用 DPAPI 文件。复核了数据库中的原报告、正文哈希以及导出的
Markdown 哈希。交付目录只收录脱敏回执和公开题目的导出报告。

### WebView2 首次联网引导

在联网的独立沙箱中，隔离旧运行时的注册项，确认默认 Loader 返回 `0x80070002`。
随后从新建的普通 Windows 账户启动原 Alpha.3 安装包，该账户此前没有自己的 WebView2。
安装程序下载并运行了微软签名的引导程序，在 `HKCU` 注册了新版 `157.0.4341.60`。
原生窗口和 API 在启动后 8.577 秒内就绪；运行中的浏览器 EXE 实际位于该用户的新安装目录。
卸载退出码为 0，客户端程序和卸载注册项清除，数据库和共享 WebView2 保留。

相同初始注册状态下，提升权限的沙箱账号也成功下载并运行了同一微软引导程序，但更新日志记录
`0x80040902`，NSIS 以 2 退出，应用程序文件未安装。两个沙箱的系统目录中都仍有旧版
`157.0.4341.46` 文件。整机从未预装过 WebView2 的场景仍待独立镜像验证。Alpha.3 安装包仍未签名。
